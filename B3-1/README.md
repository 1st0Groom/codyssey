# 🚀 Mini Redis 구축

## 1. 핵심 개념 정리

### 💡 레디스(Redis)와 인메모리(In-Memory) 키-밸류(Key-Value)
* **인메모리 (In-Memory)**: 데이터를 하드디스크가 아닌 **RAM(메모리)**에 저장하는 방식입니다. 디스크 기반 저장소보다 수백~수천 배 빠르지만, 컴퓨터가 꺼지면 데이터가 휘발된다는 특징이 있습니다.
* **키-밸류 (Key-Value)**: 사전처럼 특정 '키(Key)'를 검색하면 그에 매칭되는 '값(Value)'을 즉시 찾아내는 단순하고 직관적인 데이터 구조입니다.
* **레디스가 빠른 이유**: 하드디스크를 읽는 디스크 I/O 작업 없이, 모든 데이터를 가장 빠른 RAM에 올려두고 단순한 키-밸류 형태로 즉시 찾아내기 때문입니다.

---

### 🔄 캐시(Cache)와 메시지 브로커(Message Broker)
* **캐시 (Cache)**: 데이터베이스(DB)에서 무거운 데이터를 매번 조회하면 속도가 느려지므로, 자주 찾는 데이터를 Redis에 임시로 복사해 두고 빠르게 꺼내 쓰는 **임시 보관소** 역할을 합니다.
* **메시지 브로커 (Message Broker)**: 여러 서버가 서로 메시지나 알림을 주고받을 때, 중간에서 이를 분류하고 안전하게 전달해 주는 **우체국** 역할을 수행합니다.

---

### 🛠️ 자료구조 3대장
> ⚠️ **주의**: 파이썬 내장 `dict`나 `list`를 사용하지 않고, 아래 자료구조들을 직접 파이썬 클래스로 구현해야 합니다.

1. **해시맵 (HashMap)**
   * 키(Key)를 입력받아 수학적 계산(해시 함수)을 통해 데이터가 저장된 메모리 위치를 O(1)의 속도로 빠르게 찾아내는 구조입니다.
2. **이중 연결 리스트 (Doubly Linked List)**
   * 데이터 노드들이 기차 칸처럼 앞뒤로 양방향 연결된 구조입니다. 중간에 위치한 데이터를 빼내어 맨 앞으로 옮기는(LRU 구현에 필수적인) 작업을 매우 빠르게 처리할 수 있습니다.
3. **힙 (Heap)**
   * 데이터를 무작위로 삽입해도 내부 규칙에 의해 항상 최솟값(Min Heap) 또는 최댓값(Max Heap)이 맨 꼭대기(루트 노드)에 오도록 유지하는 자동 정렬 구조입니다.

---

### ⏳ LRU(Least Recently Used)와 TTL(Time To Live)
* **LRU (Least Recently Used)**: 메모리 용량이 가득 찼을 때, **가장 오랫동안 사용되지 않은(참조되지 않은) 데이터**부터 우선순위로 삭제하는 메모리 관리 알고리즘입니다.
* **TTL (Time To Live)**: 데이터에 "3초 뒤 자동 삭제"와 같은 만료 타이머를 설정하는 기능입니다. **힙(Heap) 구조**를 활용하면 가장 만료 시간이 임박한(빨리 죽을) 데이터를 효율적으로 관리할 수 있습니다.

---

### ⚠️ 예외 상황 (Edge Case)
정상적인 흐름에서 벗어나 프로그램의 오작동을 유발할 수 있는 극단적이거나 예외적인 상황들입니다. 철저한 예외 처리가 필요합니다.
* 이미 삭제된 키의 만료 시간(TTL)을 연장하려고 시도할 때
* 메모리 제한 설정이 `0`(무제한)일 때의 동작 처리
* 입력 값에 공백(띄어쓰기)이나 따옴표가 비정상적으로 섞여 들어올 때 등.

## 2. 자료구조 알고리즘 구현

### 1. 이중 연결 리스트
일반적인 리스트는 중간에 있는 데이터를 빼거나 맨 앞으로 넣으려면 뒤에 있는 데이터를 전부 한 칸씩 미뤄야 해서 느립니다. (시간 복잡도 O(n))
하지만 이중 연결 리스트는 기차 칸처럼 데이터들이 prev와 next 라는 연결 고리로만 이어져 있습니다.
어떤 노드의 위치만 알고 있다면 그 노드의 앞뒤 연결고리만 툭 끊어서 다른 곳에 딱 붙이면 되기 때문에 순서 변경이나 삭제가 O(1)로 가능합니다.
* 파일 경로: `data_structures/doubly_linked_list.py`

### 2. 해시맵
* 키를 해시 함수를 통해 인덱스로 변환하고, 해당 인덱스의 버킷에 데이터를 저장하는 구조입니다.
* 충돌 발생 시 체이닝(Chaining) 기법을 사용하며, 로드 팩터가 0.75를 초과하면 버킷 크기를 2배로 확장(Resize)하고 기존 데이터를 재해싱(Rehash)합니다.
* 파일 경로: `data_structures/hash_map.py`

### 3. 최소 힙
* 만료 시각을 기준으로 만료가 임박한 키가 항상 루트(가장 최상위 인덱스)에 위치하도록 이진 트리 구조로 구성한 최소 힙입니다.
* 힙 삽입 시 `_heapify_up`, 최소값 반환 및 삭제 시 `_heapify_down` 연산을 통해 힙의 불변성을 유지합니다.
* 파일 경로: `data_structures/min_heap.py`

## 3. LRU, TTL, 메모리 관리 흐름

### 1. GET 명령어 전체 흐름
1. **만료 키 사전 정리**: 호출 시점 기준 만료 시간이 지난 모든 키를 힙에서 꺼내 해시맵, 연결 리스트 및 장부에서 제거합니다 (`_clean_up_expired()`).
2. **존재 여부 확인**: 해시맵에 키가 존재하는지 판단하여, 없으면 `(nil)`을 반환합니다.
3. **LRU 우선순위 갱신**: 키가 존재할 경우, 해당 노드 위치를 이중 연결 리스트의 맨 앞(헤드 바로 뒤)으로 이동시킵니다 (`move_to_front(node)`).
4. **값 반환**: 노드에 담겨있는 실제 값을 포맷에 맞춰 반환합니다.

### 2. 메모리 초과 시 Eviction 흐름
1. `maxmemory > 0`인 상황에서 `used_memory > maxmemory`인 동안 루프를 수행합니다.
2. 이중 연결 리스트의 맨 뒤(더미 테일 바로 앞 노드)에서 가장 오랫동안 사용되지 않은 노드를 획득하고 제거합니다 (`self.dll.remove_back()`).
3. 획득한 노드의 키를 해시맵에서 완전히 제거합니다 (`self.hash_map.remove()`).
4. 방출한 데이터의 키와 값 문자열 크기만큼의 바이트 수를 총 사용량에서 감산합니다 (`self.used_memory` 차감).
5. 방출 카운터(`self.evicted_keys`)를 1 증가시킵니다.
6. 만료 타이머 장부(`self.ttl_manager.ttl_map`)에서도 해당 키를 삭제해 가비지 컬렉션을 수행합니다.

  * **DEL**: `core/redis_store.py`의 `DEL()` 메서드에서 해시맵과 이중 연결 리스트에서 해당 노드를 삭제하고 메모리를 환수하며, 만료 타이머도 정리합니다.

* **연동**: `core/redis_store.py`의 `_evict_if_needed()`, `CONFIG_SET()`, `SET()`

#### Q4. TTL 관리와 관련하여 EXPIRE, TTL 규칙이 정상 동작하며, 만료된 키가 적절히 제거되는가?
* **답변**: 네, 정상 동작합니다.

  * **TTL**: `core/redis_store.py`의 `TTL()`에서 키가 존재하지 않으면 `(integer) -2`, 타이머가 세팅되지 않은 경우 `(integer) -1`, 설정되어 있다면 남은 시간(초)을 정수로 환산하여 반환합니다.

* **연동**: `core/redis_store.py`의 `_clean_up_expired()`, `EXPIRE()`, `TTL()`, `core/ttl_manager.py` 전체

### 📋 항목 2. 기본 자료구조 구현 설명

#### Q1. 이중 연결 리스트의 노드 구조인 prev, next, data 필드와 핵심 메서드들이 O(1)로 동작하도록 어떻게 구성했는지 설명할 수 있는가?
* **설명**: `Node` 객체는 이전 노드를 가리키는 `prev` 포인터, 다음 노드를 가리키는 `next` 포인터, 데이터 속성인 `key`와 `value`를 보관합니다. `DoublyLinkedList` 생성자에서 가짜 노드인 **더미 헤드(dummy head)**와 **더미 테일(dummy tail)**을 미리 양끝단에 체이닝해 둠으로써 경계 조건(비어있는 리스트 등)을 완화합니다. 임의의 노드를 삽입하거나 삭제할 때 포인터의 앞뒤 참조(예: `node.prev.next = node.next`, `node.next.prev = node.prev`)만 교체하기 때문에, 리스트 순회 없이 모든 기본 메서드가 O(1) 시간 복잡도로 동작합니다.
* **연동**: `data_structures/doubly_linked_list.py`

#### Q2. 해시맵에서 직접 설계한 해시 함수가 어떤 입력을 받아 어떤 과정을 거쳐 인덱스를 만드는지 설명할 수 있는가?
* **설명**: `_hash_function(self, key)`는 파이썬 객체인 키(`key`)를 입력으로 받아, 이를 문자열 `str(key)`로 변환합니다. 변환된 문자열의 모든 문자에 대해 순회하며 아스크 코드 값(`ord(char)`)을 산출해 모두 누적 합산합니다. 이 누적 합을 현재 해시맵의 버킷 크기(`self.capacity`)로 나눈 나머지(`%`) 연산을 가해, 유효한 인덱스 범위(`0 ~ capacity - 1`)를 결정합니다.
* **연동**: `data_structures/hash_map.py`의 `_hash_function()`

#### Q3. 충돌 해결을 체이닝 방식으로 어떻게 구현했는지 설명할 수 있는가? 이때 버킷 내부 구조를 어떤 방식으로 선택했는지도 함께 설명할 수 있는가?
* **설명**: 동일한 인덱스를 가진 키들이 저장되려 할 때 발생하는 충돌을 해결하기 위해, 각 버킷 슬롯을 단방향 연결 리스트의 시작점으로 취급하는 **체이닝(Chaining)** 기법을 채택했습니다. 버킷 내부 구조는 포인터 형태의 `HashNode` 클래스로 구성되어 있으며, 노드의 `next` 참조 필드를 통해 충돌된 데이터들을 체인 형태로 연속적으로 이어 붙여 동적으로 할당하고 관리합니다.
* **연동**: `data_structures/hash_map.py`의 `HashNode` 클래스, `put()` 및 `get()`

#### Q4. 로드 팩터가 0.75를 초과했을 때 “버킷 2배 확장”을 어떤 절차로 수행하는지 설명할 수 있는가?
* **설명**: 로드 팩터(현재 데이터 수 `self.size` / 총 버킷 용량 `self.capacity`)가 임계치인 0.75를 초과하면 버킷 배열의 동적 확장이 일어납니다.
  1. 기존의 버킷 리스트를 임시 변수에 백업합니다.
  2. 버킷 크기 `self.capacity`를 2배로 확장하고, 새 크기에 맞는 빈 버킷 리스트(`[None] * self.capacity`)를 생성합니다.
  3. 해시 인덱스들이 재조정되므로 `self.size`를 0으로 초기화합니다.
  4. 백업된 기존 버킷을 돌며 모든 연결된 `HashNode`들을 순회하고, 새 버킷 크기에 맞추어 재해싱(Rehashing)하여 새로운 인덱스에 데이터를 삽입(`self.put()`)합니다.
* **연동**: `data_structures/hash_map.py`의 `_resize()`

### 📋 항목 3. LRU, TTL, 메모리 관리 흐름 설명

#### Q1. LRU 구현에서 “해시맵 + 이중 연결 리스트”가 각각 어떤 역할을 하며, 왜 둘 다 필요한지 설명할 수 있는가?
* **설명**:
  * **해시맵**은 키 값을 기준으로 데이터 노드를 O(1) 시간 복잡도로 빠르게 탐색/조회하기 위해 존재합니다.
  * **이중 연결 리스트**는 노드의 사용 시점에 따라 순서(최근 사용 순)를 유지하고, 가장 오래된 노드를 맨 끝(Tail 앞)에 모아두기 위해 존재합니다.
  * 만약 연결 리스트만 사용하면 검색 속도가 O(N)으로 저하되고, 해시맵만 사용하면 메모리 초과 시 어떤 데이터가 가장 오랫동안 쓰이지 않았는지의 시계열 순서 정보를 기록할 수 없으므로, 두 자료구조의 시너지를 결합해야 완벽한 O(1) 성능의 LRU 캐시 구현이 가능합니다.
* **연동**: `core/redis_store.py` 및 `data_structures/` 패키지

#### Q2. O(1) LRU 달성 원리를 “조회는 해시맵으로 처리하고, 사용 기록 갱신은 리스트 이동으로 처리한다”는 관점에서 설명할 수 있는가?
* **설명**: 데이터를 조회(`GET`)할 때 해시맵을 통해 타겟 리스트 노드를 O(1)로 찾아냅니다. 조회가 성립되면 해당 노드를 원래 리스트 링크 관계에서 툭 끊은 후 맨 앞(Head 뒤)으로 밀어 넣습니다(`move_to_front()`). 이 과정은 노드의 `prev`와 `next` 링크 포인터 4개만 수정하면 끝나기 때문에 데이터 조회와 동시에 사용 기록 갱신까지 O(1)로 달성할 수 있습니다.
* **연동**: `core/redis_store.py`의 `GET()` 및 `data_structures/doubly_linked_list.py`의 `move_to_front()`

#### Q3. TTL 관리에 힙을 사용한 이유를 설명할 수 있는가? 특히 힙이 가장 빠른 만료 시간을 빠르게 찾는 성질을 가진다는 점을 설명할 수 있는가?
* **설명**: 모든 키의 만료 시각을 일반 리스트에 모아두면, 다음으로 지워야 할 가장 임박한 키를 찾아내기 위해 전체 데이터를 대조해야 하므로 매번 O(N)의 부담이 생니다. **최소 힙(Min Heap)** 자료구조는 부모 노드가 자식 노드보다 항상 값이 작거나 같은 성질을 만족하므로, 만료 타임스탬프 값을 기준으로 데이터를 정렬해 두면 **가장 빨리 만료되는 키가 항상 맨 위(인덱스 0, 루트 노드)에 O(1)로 위치**하게 됩니다. 이 덕분에 최상단의 만료 시각과 현재 시각만 O(1)으로 대조하여 한참 남은 키가 나타나면 더이상 하위 트리 조회를 할 필요 없이 만료 검사를 안전하게 조기 종료할 수 있습니다.
* **연동**: `core/ttl_manager.py`의 `clear_expired()` 및 `data_structures/min_heap.py`

#### Q4. 메모리 초과 시 eviction 흐름을 단계별로 설명할 수 있는가? 이때 used_memory 산정 및 갱신, LRU 제거, evicted_keys 증가까지 포함하여 설명할 수 있는가?
* **설명**:
  1. 새로운 키가 `SET`되거나 메모리 상한치가 설정될 때 현재 `used_memory`가 `maxmemory` 한계를 넘는다면 Eviction 루프에 들어섭니다.
  2. 이중 연결 리스트의 테일 칸 바로 직전 노드를 삭제하여 방출 대상을 지정하고 제거합니다 (`self.dll.remove_back()`).
  3. 제거 대상 노드의 키를 사용해 메인 해시맵(`self.hash_map.remove(key)`)에서 데이터를 완전 제거합니다.
  4. 방출된 키와 값 문자열 크기만큼 바이트 수를 연산하여 총 사용량에서 감산 갱신합니다 (`self.used_memory -= self._calc_memory_(key, value)`).
  5. 방출 횟수 카운터 `self.evicted_keys`를 1 증가시킵니다.
  6. 만료 타이머 장부(`self.ttl_manager.ttl_map`)에 해당 키가 존재하면, 해당 키의 알람 장부 기록도 삭제해 가비지 컬렉션을 완수합니다.
* **연동**: `core/redis_store.py`의 `_evict_if_needed()`

#### Q5. GET 명령어의 전체 흐름을 순서대로 설명할 수 있는가? 즉, TTL 확인, 만료 여부 판단, 만료된 키 삭제, 값 반환, LRU 갱신 조건을 순서대로 설명할 수 있는가?
* **설명**:
  1. **만료 키 사전 제거**: `GET` 호출 시점의 현재 시각(`time.time()`)을 기준으로, 최소 힙의 루트를 반복 대조하여 만료 시간이 경과한 키들을 해시맵, 리스트, 힙 및 알람 장부에서 게으른 삭제(Lazy Expiration)로 일괄 소멸시킵니다.
  2. **존재 여부 대조**: 해시맵에 조회 대상 키가 들어있는지 탐색합니다. 없다면 `"(nil)"`을 반환하고 동작을 끝냅니다.
  3. **LRU 정보 갱신**: 키가 존재한다면 해당 노드를 이중 연결 리스트의 맨 앞(기관차 바로 뒤)으로 자리를 이동시켜 최근 참조 사실을 기록합니다.
  4. **값 반환**: 노드 내부에 저장된 실제 값에 큰따옴표를 붙여 클라이언트에게 반환합니다.
* **연동**: `core/redis_store.py`의 `GET()`

### 📋 항목 4. 확장 사고 및 구조 개선 설명

#### Q1. “만약 LRU 대신 LFU 정책을 구현한다면 자료구조를 어떻게 변경해야 하는가?”라는 질문에 합리적으로 답변할 수 있는가?
* **답변**: LFU(Least Frequently Used) 캐시 구현 시, 각 데이터가 참조된 누적 횟수(Frequency) 정보가 추가로 기록되고 관리되어야 합니다.
  * **힙 기반의 변경**: 데이터 노드에 `access_count` 속성을 추가하고, 힙 자료구조에 `(access_count, key)` 구조로 노드들을 넣어서 빈도가 가장 적은 키가 항상 힙 루트에 오도록 설정합니다. 다만, 조회나 저장 시 횟수가 증가할 때마다 힙 재배치 연산(Heapify, O(log N)) 비용이 소모됩니다.
  * **O(1) 해시맵 + 이중 연결 리스트 조합(LFU)**: 참조 횟수별 이중 연결 리스트들을 해시맵(`frequency_map`)으로 보관합니다. 데이터가 참조될 때 기존 횟수 리스트에서 노드를 이탈시키고 `이전 횟수 + 1` 리스트의 헤드 뒤로 삽입하는 기법을 구현하면 데이터 조회 시 LFU 우선순위 업데이트를 완벽히 O(1) 속도로 처리할 수 있습니다.

#### Q2. “데이터가 10만 건으로 늘어나면 현재 구조에서 병목이 될 수 있는 부분은 어디이며, 어떻게 개선할 수 있는가?”라는 질문에 답변할 수 있는가?
* **답변**:
  * **병목 1 (해시맵 검색 지연)**: 현재 아스키 코드 값을 단순 누적 합산하는 문자열 해시 함수는 해시 충돌(Hash Collision)이 매우 빈번하게 발생하여 체이닝 리스트 길이가 길어지며 검색 시간이 O(1)에서 O(N)에 가깝게 저하됩니다.
    * *개선방안*: MurmurHash3, FNV-1a 등 무작위 분산성이 탁월한 프로덕션급 해시 함수로 교체 적용합니다.
  * **병목 2 (게으른 만료 처리 병목)**: 만료 시간이 동일하거나 유사하게 겹친 대규모의 데이터가 쌓여 있을 때, 특정 명령어 실행 시 `_clean_up_expired()`에서 동기적으로 힙 `pop` 연산을 지속해 정리 작업을 진행하면 순간적으로 스레드가 블로킹되어 레이턴시가 튈 수 있습니다.
    * *개선방안*: 명령어 실행 시에는 게으른 만료 처리를 일정 개수 제한하여 끊어 수행하고, 백그라운드 스레드를 띄워 일정 주기마다 임의의 키들을 대상으로 백그라운드 액티브 만료(Active Expiration)를 비동기로 병행합니다.

#### Q3. “used_memory에 자료구조 오버헤드까지 포함하는 모델로 바꾸면 무엇이 달라지고, 공정한 비교 또는 채점을 위해 어떤 보정이 필요할지” 설명할 수 있는가?
* **답변**:
  * **달라지는 점**: 현재 방식은 단순 데이터 문자열 바이트 수만 `used_memory`에 환산하고 있으나, 실제 런타임 환경에서는 `HashNode`, `Node`(연결 리스트), 최소 힙 트리 노드 및 각 필드의 객체 레퍼런스 포인터가 RAM 메모리를 상당히 점유합니다. 물리 오버헤드를 가산하면 키-밸류 저장 시 계산되는 소모 메모리가 크게 치솟고, 데이터 방출(Eviction)이 설정된 maxmemory 범위 내에서 훨씬 빠르게 호출됩니다.
  * **보정 방법**: 자료구조 오버헤드를 정확하게 합산하기 위해 파이썬 시스템 모듈(`sys.getsizeof()`)을 통한 실측 오버헤드 값을 사용하거나, 노드당 고정적인 가상 오버헤드 바이트 상수(예: 해시 노드 32바이트, 양방향 포인터 노드 48바이트 등)를 미리 규정한 표준 가이드 스펙을 산정하여 가산하도록 채점 공식을 보정하여 비교의 형평성을 맞추어야 합니다.
